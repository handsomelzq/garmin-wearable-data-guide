# Garmin 手环数据提取与清洗：可复用流程

## 1. 先确定观测协议

一次任务至少应明确：哪些人实际佩戴手环、观测开始日期、包含到哪一天、北京时间或其他时区、纳入的心率覆盖阈值、设备型号，以及账号访问是否已经获得授权。

本实现的时区为 `Asia/Shanghai`，区间采用 `[开始日00:00, 结束日00:00)`。正式数据包含左端，不包含右端。若要包含最后一个观测日全天，`--end` 写次日日期。

`wears_band=true` 的对象进入账号检查；心率缺失达到默认80%后排除。阈值可通过 `--missing-threshold` 改变，属于研究规则，不是医学诊断。

## 2. 准备环境与私有工作目录

使用 Python 3.12 与 `uv`。在终端进入代码目录后运行 `uv sync`；不要把依赖装到系统 Python。依赖包括 `garminconnect`、官方 FIT SDK、pandas 与 openpyxl。

仓库只存代码和文档。另建 `../private_work`，放账号配置、登录缓存、下载数据及成果。即使使用了 `.gitignore`，也不应把真实数据复制进准备发布的目录。

配置示例使用 `SAMPLE_001` 占位，不是真实受访者。`account_env` 与 `password_env` 是环境变量的**名称**，不是账号和密码。`is_cn=true` 使用中国区，国际账号用 `false`。

环境变量可在自己的终端用隐藏输入提供。账号密码不同的对象使用不同变量；不要把含密码的导出命令、终端截屏或 shell 历史上传到仓库。

## 3. 登录后先做心率初筛

官网心率曲线是采样点序列。已验证设备通常每120秒一个点，但数据缺失时可能省略整个时间槽，因此不能用“非空记录数/返回数组长度”判断覆盖率。

默认规则：每天预期720个两分钟槽位。把真实时间戳归入固定的本地两分钟网格，每槽只算一次有效心率。有效值采用项目规则 `30≤HR<255`；`0` 以及 SDK 的无效值不进入统计。

```text
预期槽位 = 观测天数 × 86400 / 采样秒数
缺失率 = 1 − 有有效心率的槽位数 / 预期槽位
估计覆盖分钟 = 有效槽位 × 采样秒数 / 60
```

最后一项只是筛选覆盖估计，不会把一个官网点复制成两个分钟读数。缺失率达到阈值即排除；例如阈值0.8对应“80%以上”。

所有天的心率接口都成功后，才能给出完整区间缺失率。登录失败、验证码未提供、接口超时或权限失败标记为未知，不当作100%缺失。实际众数采样间隔与配置不同的对象标为 `screen_cadence_review`，先核对设备和曲线再处理。

被排除对象只保存心率初筛与状态，不继续完整下载。以前某次分组的排除名单不能代替本次观测期的实测筛选。

## 4. 下载什么

通过心率初筛后，下载以下资料：

| 类别 | 原始格式 | 用途 |
|---|---|---|
| 日常监测 | ZIP中的FIT | 心率、压力、累计计数及设备实际写入的其他消息 |
| 运动记录 | 活动摘要JSON与原始FIT | 一项活动的摘要和活动内逐点记录 |
| 官方日汇总 | JSON | 总步数、距离、热量、强度分钟、楼梯高度、身体电量 |
| 睡眠 | JSON | 入睡/起床、深睡/浅睡/REM、睡眠相关心率与压力 |
| 心率、压力、身体电量、血氧、呼吸、HRV、步数、楼梯、强度分钟 | JSON | 原始补充数据及核查依据 |

额外保存结束日的边界 FIT 与睡眠 JSON。午夜的累计值可能属于前一天，最后一晚也可能在次日醒来；这些文件有助于核查，但不会新增正式观测期外的日级或分钟行。

成功返回的 JSON 和 FIT 完成标记用于断点续传。失败不会当作成功，状态按数据类别和日期写入日志。404说明该端点当时没有可下载资料，不能仅凭404断定未佩戴。

一个私有目录只用于同一批账号、日期和筛选规则。程序保存本地账号摘要用于核对缓存归属；更换账号、日期或规则时使用新的私有目录，避免误复用旧令牌与旧结果。摘要同样属于私有资料，不能公开。

网络请求失败后有限重试。验证码账号可加 `--interactive-mfa`，在终端单独处理。运行环境不能联网时应先解决网络权限，不能把所有账号错误计为研究对象缺失。

## 5. FIT解码为什么要按消息拆表

FIT是二进制事件流，不是一张连续的二维表。同一文件可混装 `monitoring`、`stress_level`、`record`、`session`、`lap`、设备信息和未知消息。字段不同的消息不能直接挤到同一张宽表中。

`fit2csv.py` 默认把每种消息写成独立CSV，附 `subject_id`、`source_file`、当地时间和日期。未知消息也保留，避免因为暂时不了解字段而丢失原始信息。

SDK解析时会缩放数值、转换枚举和UTC时间戳。先检查FIT完整性，再重置流指针进行读取；没有重置流指针可能导致空解析。CRC问题、解码异常及相关告警应留日志，不能静默当作无观测。

部分监测记录只有16位压缩时间戳，需要从之前的完整时间戳逐条推进：

```text
last = last + ((timestamp_16 − (last & 65535)) & 65535)
```

这会处理16位回绕。压缩时间戳还原属于解码，不是插值心率。还原后的记录仍只代表设备真实写下的观测。

## 6. 时间、重复与有效值

- 原始FIT时间为UTC；先转北京时间再分日、归分钟。字段末尾 `_utc` 明确保持UTC。
- 多个导出包可能重复包含同一条原始记录。心率按“编号+原始时刻+心率值”去重；压力按除文件名外的完整记录去重。不能只按时间戳删除所有行。
- 心率0不作为0 bpm；压力有效范围0—100，负值和异常值不参与均值；血氧仅保留大于0且不超过100的真实读数。
- 同一分钟多个有效读数取均值。只有一个读数时，均值就是该值；没有读数留空。原始CSV始终保留，可按新研究方案重新聚合。

分钟均值没有进行跨分钟平滑，也没有代表这一整分钟都持续维持该数值。整理为分钟行不等于设备原生每分钟采样。

## 7. 生成分钟级面板

按编号创建完整分钟网格，键为 `subject_id + minute_start_local`。每名纳入对象的行数应等于观测天数×1440，同一天固定1440行。

心率来自FIT `monitoring.heart_rate`，压力来自 `stress_level`，血氧来自 `spo2_data.reading_spo2`。每分钟分别取有效读数均值，保留心率计数、有效压力计数和原始压力计数。

血氧合并保留实际读数的本地/UTC时间、confidence和测量模式。多个模式取去重集合；官方日均、夜均或小时均不扩展成分钟读数。没有血氧时整列可以为空。

压力中的厂商字段2和4保留该分钟最后一个非空值，不平均代码；字段3保留项目对身体电量的解释。这些字段未被作为跨设备通用的官方生理定义。

分钟表按编号和时间排序。来源文件字段用于回溯原始FIT；不同受访者相同文件名也不会混在一起，因为下载和解析目录按编号隔离。

## 8. 生成日级数据

日级键为 `subject_id + local_date`，睡眠按醒来日合并。

正式总步数、距离、活动热量、活跃时间、强度分钟、楼梯高度及身体电量以服务器日值为准。活跃秒数为 `activeSeconds + highlyActiveSeconds`；字段缺失时不强行补0。

本实现的日级平均、最小、最大心率来自FIT有效观测，和已确定的表格口径保持一致。官网日摘要与两分钟曲线可能有不同极值，不能悄悄把其中一种覆盖另一种。

步数分项只保留 `running_steps`、`walking_steps` 和 `official_total_steps`。分项为FIT重算结果；正式总步数来自 `totalSteps`。分项之和不强制调整成官方总数。

`weighted_intensity_minutes = moderate_intensity_minutes + 2 × vigorous_intensity_minutes`。加权强度分钟不是实际计时器分钟。楼梯变量单位为米，是上/下高度，不是楼层数。

身体电量是算法分值，最高/最低/充电/耗电/醒来值含义不同，不能当作热量或电池容量。

## 9. 累计计数器的两个问题

本项目验证过的监测导出中，午夜记录可能携带前一天的最终累计数，所以累计计数的归属日按“本地时间减1秒”计算。这个偏移只用于累计字段；心率、压力、运动开始时间不减1秒。

计数器按活动类型分别累计。步数、距离和活动热量不能只取所有记录中最大的一条；需要分类型取值，再汇总。中途重启、重新配对或切换设备还可能重置计数器。

分段正增量重算会保留核查依据，但不保证重置日的真实总量。正式总量使用服务器日值。不同设备的午夜约定和隐藏字段应重新验证，不能把本设备规则当FIT协议对所有设备的要求。

## 10. 睡眠为什么需要JSON

已验证设备的 `sleep_level` 主要出现清醒/无法测量标记，不能据此恢复完整深睡、浅睡与REM。服务器睡眠JSON提供这些分期和入睡/醒来时刻。

`sleepTimeSeconds/60` 是睡眠时长；入睡至起床的间隔还可能包含清醒和无法测量时间，不能直接替代。`*TimestampLocal` 是当地钟表时间的编码，不能解析后再加8小时。

`sleep_record_valid` 是项目质控：如支持REM却睡眠较长而REM为0，或FIT在该时段大量标为无法测量，会产生异常标记。值为False不代表原始睡眠数据被删掉；具体原因保留在睡眠摘要CSV。

多个对象同一进程处理时，要清除按对象隔离的睡眠质控缓存，避免把上一人的FIT标记用于下一人。

## 11. 活动表和扩展资料

活动摘要一项活动一行，主键为编号+活动ID。距离从米转千米；步长从摘要里的厘米转米；配速由速度m/s计算 `1000/(speed×60)`，存为数值min/km。

活动步频字段本身已经是步/分钟，不再乘2。活动计时、移动时间和总经过时间分别保存。摘要没提供TSS或减压标志时留空，不人为填0或否。

活动FIT中的 `record`、`lap` 和 `session` CSV 可支持进一步的活动内轨迹或分段分析，但不与“每项活动一行”的摘要混用。没有主动启动运动时可以没有活动记录。

呼吸和HRV是否可得取决于设备与记录方式。下载到JSON不代表每个字段都非空；本实现保存原始补充资料，尚未把它们增加到固定三表中。

## 12. 输出与核查

运行 `process.py` 先产生三表CSV和缺失CSV，再用 `export_excel.py` 流式写入两个Excel工作簿。大型分钟面板不应全部加载成带样式的内存工作簿。

数据工作簿：`README`、`daily_data`、`minute_data`、`activities`。首页中文说明列出每个变量的含义、单位、来源和处理规则。数据表第2行是字段名，Python可用 `pd.read_excel(..., skiprows=1)`。

缺失工作簿保留所有对象，包括排除或失败对象；同时给出逐日官网心率、分钟缺失情况、处理问题和接口状态。不要只报告纳入对象，让其他对象从检查表中消失。

交付前至少核对：账号/编号一致、每人每天行数、主键无重复、观测期边界、时间排序、数值范围、缺失分母、原始文件来源以及日级最大心率的口径。真实记录的缺失应保留为空，而不是为了表格好看而插值。

## 13. 保留私有工作目录

```text
private_work/
├── accounts.json              环境变量名称映射；不要公开
├── run_config.json            本批次时间、时区与筛选规则
├── .tokens/                   登录缓存，不公开
├── screening/                 每人的初筛原始记录和状态
├── data/<subject_id>/
│   ├── raw/                   日常与活动FIT、活动摘要
│   ├── csv/                   全部FIT消息类型CSV
│   ├── official/json/         服务器日值
│   ├── sleep/                 睡眠JSON、摘要及分期
│   ├── connect_extra/         其他补充JSON
│   ├── analysis/              逐人整理结果
│   └── audit/                 处理日志及下载标记
├── logs/                      接口下载状态
└── results/                   合并CSV和两份Excel
```

发布教程时不要复制这个工作目录。仅上传代码目录中的允许文件，执行隐私检查，再检查暂存区。公开示例CSV必须只保留一行表头。
